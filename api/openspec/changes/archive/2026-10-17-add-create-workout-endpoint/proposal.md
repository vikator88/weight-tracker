# Proposal

## Why

`Workout.Create` exists in the domain, but no API call can create a workout. Workouts only enter the system through the seed. This change exposes creation over HTTP so users can log their own workouts and trainers and admins can prescribe workouts to others. Later endpoints that add exercises to a workout depend on it.

Source plan: `.stpr/plan/openspec/proposal-change-add-create-workout-usecases-endpoints.md`.

## What Changes

- New endpoint `POST /workouts` (authenticated, any role) with body `CreateWorkoutRequest { userId?: Guid, trainerId?: Guid, workoutDate: DateOnly }`. Returns `201 Created` with the new workout as a `WorkoutResponse` (no exercises yet).
- New use case `CreateWorkoutUseCase` in `WeightTracker.Application/UseCases/Workouts`. It mutates state only through `Workout.Create`.
- **Who owns and who prescribes**, by caller role (agreed with the user):
  - `USER`: owner is the caller, trainer is `null`. `userId` may be omitted or equal to the caller. A different `userId`, or any `trainerId`, is rejected with `400`.
  - `TRAINER`: `userId` is required and becomes the owner, and the caller becomes the trainer. `userId` equal to the caller is rejected with `400`, because trainers cannot create workouts for themselves. Any `trainerId` is rejected with `400`, because only an admin may set it. The owner must have the `USER` role (`403` otherwise), since trainers cannot create workouts for other trainers or admins.
  - `ADMIN`: `userId` is required and becomes the owner. `userId` equal to the caller is rejected with `400`, because admins cannot create workouts for themselves. `trainerId` is optional. When it is given, it must reference a user with role `TRAINER` or `ADMIN` (`400` otherwise) and must differ from `userId` (`400`, the existing domain rule).
  - An owner `userId` that does not exist returns `404`.
- New Application exception `InvalidWorkoutAssignmentException` mapped to `400`. It covers the role-dependent body errors above.
- No schema change, no migration, no new seed data.

## Capabilities

### New Capabilities

- `workout-creation`: creating a workout and deciding its owner and prescribing trainer from the caller's role and the request.
  Canonical references: the `Workouts` aggregate (`Workout.Create`) and `WorkoutTests` (template-backed). `WorkoutsController` and `CreateSuperSeriesUseCase` for the mutating controller action and use case shape (skeleton-backed). `ExceptionMapper` for the new mapping. `AuthEndpointsTests` (template-backed) and `SuperSeriesCreateEndpointTests` (skeleton) for the endpoint test matrix.

### Modified Capabilities

None. `workout-editing` governs changes to an existing workout and does not apply to creation.

## Identifiers and mutability

| Identifier | Owner | Mutable? |
| --- | --- | --- |
| `Workout.Id` | `Workout` aggregate, generated by `Id.New()` | Immutable. Never supplied by the client. |
| `Workout.UserId` (owner) | `Workout` | Immutable once created |
| `Workout.TrainerId` (prescriber) | `Workout` | Immutable once created. No operation changes it. |

## Conflicts with the source plan, template or invariants

- **DTO name.** The source plan calls the request `CreateSuperseriesRequest`. That name is already taken by the superseries endpoint and is clearly a copy slip. The request is `CreateWorkoutRequest`.
- **Self-created workouts for trainers and admins.** The source plan reads "userId comes from authenticated user if a user is creating a workout for themselves", which could cover any role. The user decided that only `USER` callers create their own workouts. Trainers and admins must name another owner. This narrows `Workout.Create`, which allows `trainerId = null` for any owner, so the rule lives in Application, not Domain.
- **Status codes.** Regular-user and trainer misuse of `userId`/`trainerId` returns `400` by user decision, not `403`. The only `403` is a trainer targeting a non-`USER` owner, because that is a permission over another user, not a malformed assignment.
- **Identifier validation.** Invariant §1 requires external identifiers to be validated before use, so `userId` is looked up (`404`) and an admin-supplied `trainerId` is checked through the existing `IUserRepository.IsTrainerOrAdmin` (`400`).
- **Tests.** The source plan mentions E2E tests. The repository has no E2E tier, and AGENTS.md defines only unit and integration tests, so E2E is out of scope. "Integration tests do not need seed data" is respected: the seeded `USER`, `TRAINER` and `ADMIN` reach every branch.

## Out of scope

- Adding, removing or reordering exercises in the created workout.
- `GET /workouts/{id}`. There is no single-workout read route, so the `201` response carries no `Location`.
- Changing the owner or trainer of an existing workout.
- E2E tests.

## Acceptance criteria

- `POST /workouts` behaves as specified in `specs/workout-creation/spec.md` for every role.
- The created workout appears in `GET /workouts` for its owner, for its trainer (when set) and for admins, and is persisted with the date only.
- The route carries `401` (no token), `401` (invalid token), `400` (structural and assignment errors), `403` and `404` cases, plus success for each role.
- Unit tests cover every branch of `CreateWorkoutUseCase`. `WorkoutTests` already covers `Workout.Create`.
- `dotnet test WeightTracker.slnx` passes with Docker running, and the template parity check reports no drift.

## Impact

- **Api**: `WorkoutsController` (new `Create` action), `Dtos/CreateWorkoutRequest`, `ExceptionMapper` (1 new mapping), `Program.cs` (register `CreateWorkoutUseCase`).
- **Application**: `CreateWorkoutUseCase`, `InvalidWorkoutAssignmentException`. Reuses `IWorkoutRepository.Save`, `IUserRepository.GetById` and `IUserRepository.IsTrainerOrAdmin`.
- **Domain**: no change.
- **Infra**: no change (no migration, no seed).
- **Tests**: unit (`Application/Workouts/CreateWorkoutUseCaseTests`), integration (`Workouts/WorkoutCreateEndpointTests`).
