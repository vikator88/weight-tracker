# Proposal

## Why

Every protected controller resolves its caller by itself. `WorkoutsController` parses the `sub` and role claims in a private `TryReadCaller` and repeats the check in each action. `ExercisesController` reads nothing. Neither checks that the user in the token still exists, so a well-signed token keeps working after its user is gone. This change moves caller resolution into one shared base controller and adds an Application use case that checks the user exists, so the API never needs a repository.

Source plan: `.stpr/plan/openspec/proposal-change-refactor-controllers-to-inherit-authorized.md`.

## What Changes

- New abstract base controller `AuthorizedController` in `WeightTracker.Api/Endpoints/`. It is `[Authorize]` at class level. Before each protected action it reads the caller id from the validated token, resolves the user through the new use case, and exposes the result as a protected `CurrentUser` property. If the token has no usable subject, or the user does not exist, the action does not run and the response is `401`.
- On `[AllowAnonymous]` actions the base controller does not resolve anything, and `CurrentUser` is `null`.
- New use case `GetAuthenticatedUserUseCase` in `WeightTracker.Application/UseCases/Auth`. It loads the user by id through `IUserRepository` and returns an `AuthenticatedUser` record (id, email, name, surname, role). It never returns the `User` aggregate, so the password hash stays out of the API. A missing user raises the new `AuthenticatedUserNotFoundException`, which `ExceptionMapper` maps to `401`.
- `WorkoutsController` and `ExercisesController` inherit `AuthorizedController`. `WorkoutsController` drops `TryReadCaller` and passes `CurrentUser.Id` and `CurrentUser.Role` to its use cases. Use case signatures do not change.
- `AuthController` (`/auth/signup`, `/auth/login`, `/auth/refresh`) does **not** inherit it and stays public.
- Behavior change: a valid token whose user no longer exists now gets `401` on every protected route. Before, it reached the use case.
- The caller's role now comes from the stored user, not from the token, both for use cases and for role-gated routes. New attribute `[RequireRole(...)]` replaces `[Authorize(Roles = ...)]` on the Exercises write routes. `AuthorizedController` checks it after the user lookup, so the order is: no token or invalid token `401`, user no longer exists `401`, role not allowed `403`.
- No schema change, no migration, no new seed data, no change to the OpenAPI security scheme.

## Capabilities

### New Capabilities

- `authenticated-caller`: how protected routes establish who the caller is. A valid token must belong to a user that still exists, otherwise the request is rejected with `401`, and public routes are not affected.
  Canonical references: `WorkoutsController` (skeleton-backed) for controller shape, `[ProducesResponseType]` and `ExceptionMapper` use. `LoginUseCase` and `AuthResult` (skeleton-backed, `Auth` row of the reference map) for an Auth use case that returns an Application record. `ExceptionMapper` for the new mapping. `AuthEndpointsTests` (template-backed) for the per-route `401` matrix. `LoginUseCaseTests` for the use case unit tests.

### Modified Capabilities

None. `workout-creation`, `workout-editing` and `workout-superseries` keep their requirements. Their `401` scenarios still hold, and the new stale-user rule is owned by `authenticated-caller`.

| Identifier | Owner | Mutable? |
| --- | --- | --- |
| `User.Id` (token `sub`) | `User` aggregate, generated by `Id.New()` | Immutable. Read only, used to look the caller up. |

No identifier is introduced or changed.

## Conflicts with the source plan, template or invariants

- **Name `AuthController`.** The source plan calls the base class "Auth Controller". `WeightTracker.Api/Endpoints/Auth/AuthController` already exists (login, signup, refresh), and the source plan itself says it must not inherit the base. The base class is named `AuthorizedController`, which matches the source plan's file name.
- **Property `User`.** The source plan asks for a protected `User`. `ControllerBase.User` already exists (the `ClaimsPrincipal`), and hiding it would break `[Authorize]`-related code that reads claims. The property is named `CurrentUser`.
- **Location.** The source plan puts the base class in `WeightTracker.Api/Endpoints`. Invariant §2 says "one folder in Endpoints per resource". The base is not a resource, so it sits at the root of `Endpoints/` as a single file, not in a resource folder.
- **401 for a missing user.** Invariant §2 requires failures detected in Application to be custom exceptions mapped by `ExceptionMapper`. The existing `UserNotFoundException` maps to `404`, which is wrong for a caller. A new `AuthenticatedUserNotFoundException` maps to `401`.
- **Role source.** The source plan does not say where the role comes from. The stored user's role is used, because the use case already loads the user. It also decides role-gated routes, so a removed user is rejected with `401` before any `403`. Today no operation changes a role.
- **Exercises public reads.** The source plan says Exercises must inherit the base. `GET /exercises` and `GET /exercises/{id}` stay `[AllowAnonymous]` and stay public.
- **Template and invariants.** `WorkoutsController` is the canonical controller reference and its "claims to use case" description will be out of date. The reference map row in `.stpr/template/README.md` and the API Layer rules in `STPR_INVARIANTS.md` are updated so later controllers inherit the base instead of reading claims.

## Out of scope

- Changing use case signatures to take an `AuthenticatedUser` instead of `(callerId, callerRole)`.
- A user deletion endpoint.
- Caching the user lookup across requests.

## Acceptance criteria

- `WorkoutsController` and `ExercisesController` inherit `AuthorizedController`. `AuthController` does not. No controller parses claims itself.
- Every protected Workouts and Exercises route returns `401` for a valid token whose user no longer exists, in addition to its existing `401` (no token) and `401` (invalid token) cases.
- Public routes (`/auth/*`, `GET /exercises`, `GET /exercises/{id}`) behave as before.
- Unit tests cover both branches of `GetAuthenticatedUserUseCase`. `ExceptionMapperTests` covers the new mapping.
- The full `dotnet test WeightTracker.slnx` passes with Docker running, and the template parity check reports no drift.
