# Proposal

## Why

The only way to create a user today is self-service `POST /auth/signup`, which forbids the `ADMIN` role and logs
the new user in. Administrators need to create accounts for other people, of any role, without the endpoint
issuing a session for the account it creates.

## What Changes

- New protected route `POST /users`, restricted to callers whose stored role is `ADMIN`.
- Body: `email` and `password` required, `role` required (`USER`, `TRAINER` or `ADMIN`), `name`, `surname` and
  `dateBirth` optional.
- Responds `201 Created` with the created user's `id`, `email`, `name`, `surname`, `dateBirth` and `role`. No
  access token, refresh token or any other authentication data, and no refresh token is persisted.
- Errors: `400` for invalid input (malformed email, weak password, invalid name, missing required field, unknown
  role), `409` for an email already registered, `403` for non-admin callers, `401` without a valid token.
- `POST /auth/signup` is unchanged: it still rejects `ADMIN` and still logs the new user in.
- `PUT /users/me` and `GET /users/me` are unchanged.

## Canonical Template Mapping

- `CreateUserUseCase` -> `src/WeightTracker.Application/UseCases/Auth/SignupUseCase.cs` -> same creation flow on the `User` aggregate, minus the token issuing and the `ADMIN` restriction.
- `UsersController.Create` -> `.stpr/template/src/WeightTracker.Api/Endpoints/Workouts/WorkoutsController.cs` (create actions) -> protected `AuthorizedController` action returning `201`, every catch through `ExceptionMapper.Map`.
- Admin-only access -> `src/WeightTracker.Api/Endpoints/RequireRoleAttribute.cs` with `AuthorizedController` -> existing role mechanism that answers `401` before `403`; first use on a controller action.
- DTOs -> `src/WeightTracker.Api/Endpoints/Users/Dtos` -> request/response record and `From` mapping shape.
- Tests -> `test/WeightTracker.Unit/Application/Auth/SignupUseCaseTests.cs`, `.stpr/template/test/WeightTracker.Integration/Auth/AuthEndpointsTests`, `test/WeightTracker.Integration/Users/UserProfileEndpointTests.cs` -> unit shape with mocked ports, and `401`/`403` matrix with persisted-state checks.

No conflict with `.stpr/template/STPR_INVARIANTS.md` or the template was found.

## Module Classification And Identifiers

- `Users` is a mutable aggregate, not a catalog. This change adds a creation path only; no new table or column.
- `User.Id` is the technical identifier, generated by `Id.New()` inside `User.Create`, immutable.
- `User.Email` is the unique business identifier, immutable after creation.

## Impact

- API: new `POST /users`; the OpenAPI document gains that path, so the front's snapshot will need a refresh in
  its own plan.
- Code: `Application/UseCases/Users` (new use case), `Api/Endpoints/Users` (new action and DTOs), `Program.cs`
  (registration). No changes to the domain, infrastructure, `ExceptionMapper` or migrations.
- Tests: new unit tests for the use case, new integration tests for the endpoint, OpenAPI document test entries.

## Acceptance Criteria

- An `ADMIN` can create a user of each role, and the created user can log in with the given password.
- Optional fields can be omitted; the user is created with empty name/surname and no meaningful date of birth.
- The response contains no token fields and the caller's own session is unaffected.
- `USER` and `TRAINER` callers get `403`; anonymous or invalid-token callers get `401`; nothing is persisted in
  those cases.
- All unit and integration tests pass.
