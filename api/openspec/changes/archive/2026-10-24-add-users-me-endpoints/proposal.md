# Proposal

## Why

Clients (front and backoffice) need to show who is logged in and let that user edit their own profile. Today there is no endpoint that returns the caller's stored data, so a client can only guess it from the token, and there is no way to change a user's name or surname after signup.

## What Changes

- Add `GET /users/me`: returns the caller's `id`, `email`, `name`, `surname` and `role`, resolved from the access token.
- Add `PUT /users/me`: replaces the caller's `name` and `surname` and returns the updated profile in the same shape as `GET /users/me`.
- Both routes are protected, act only on the caller, and take no user id in the route.
- `role` and `email` cannot be changed through `PUT /users/me`. The request body does not carry them; if a client sends them they are ignored.
- New aggregate action method `User.UpdateProfile(PersonName name, PersonName surname)`.
- No migration, no new table or column, no new repository method.

## Capabilities

### New Capabilities
- `user-profile`: the authenticated caller reading and editing their own profile, which fields are exposed, which are editable, and which are protected from change.

### Modified Capabilities
- None. `authenticated-caller` already covers `401` without a token, with an invalid token, and for a removed user on every protected route; the new routes follow it without changing it.

## Module Classification

- Users domain (`src/WeightTracker.Domain/Users`): **mutable aggregate**. `User` gains an action method; it is not a catalog.
- Users application (`src/WeightTracker.Application/UseCases/Users`, new folder): `UpdateMyProfileUseCase` mutates the aggregate. The read side is served by the existing `GetAuthenticatedUserUseCase`, which is **publicly read-only only**, not catalog-like.
- Users API (`src/WeightTracker.Api/Endpoints/Users`, new folder): REST controller with protected routes only.
- Infra (`src/WeightTracker.Infra/Repositories/UserRepository.cs`): unchanged; `Save` already updates an existing user.

## Canonical Template Mapping

- `user-profile` domain -> `Workouts` aggregate (`.stpr/template/src/WeightTracker.Domain/Workouts`, template-backed) -> action method that receives value objects and protects the action semantics. `Exercise.Update` is the closest skeleton-backed example of replacing attributes.
- `user-profile` application -> `UpdateExerciseUseCase` (`src/WeightTracker.Application/UseCases/Exercises`, skeleton-backed) -> load aggregate, build value objects, call the action method, `Save`, `IUnitOfWork.SaveChangesAsync`.
- `user-profile` API -> `WorkoutsController` (`src/WeightTracker.Api/Endpoints/Workouts`, skeleton-backed) -> inherits `AuthorizedController`, reads the caller from `CurrentUser`, every catch goes through `ExceptionMapper.Map`. Request DTO shape follows `ExerciseRequest` (structural `[Required]` only).
- `user-profile` tests -> `AuthEndpointsTests` (401 matrix) and `ExerciseUpdateEndpointTests` (PUT shape, read-back after write) for integration; `WorkoutTests` for the Arrange/Act/Assert aggregate unit test.

No conflict with `STPR_INVARIANTS.md` or the template was found.

## State And Mutability

- `PUT /users/me` changes `users.name` and `users.surname` of the caller only.
- `id`, `email`, `role`, `date_birth`, `password_hash` and `created_at` are never changed by this change.

## Roles And Visibility

- Any authenticated user (`USER`, `TRAINER`, `ADMIN`) reads and edits their own profile.
- No caller reads or edits another user's profile; the target is always the caller resolved by `AuthorizedController`.
- `403` and `404` do not apply: every caller may act on themselves, and a caller whose user no longer exists is already `401`.

## Business Identifiers And Mutability

- `User.Id`: technical identifier, generated by `Id.New()`, **immutable**.
- `User.Email`: unique business identifier, **immutable** in this change. Changing it is a separate future flow under `/auth`.

## Assumptions

- "Profile is forbidden to change" in the brief means **role**.
- Unknown body fields (`role`, `email`) are ignored, not rejected with `400`. Confirmed with the user.
- `PUT` is a full replacement of the editable profile: both `name` and `surname` are required.
- The source brief named a `GetMyProfileUseCase`. It is not created: `GetAuthenticatedUserUseCase` already loads exactly these fields for every protected request, so `GET /users/me` maps `CurrentUser` and avoids a second query. See design.md.

## Out Of Scope

- Changing the email (future `/auth` flow), the role, the password or the date of birth.
- Reading or editing another user's profile (`/users/{id}`).

## Impact

- Domain: `User.UpdateProfile`.
- Application: new `UseCases/Users/UpdateMyProfileUseCase` and its input DTO.
- API: new `UsersController`, `UpdateProfileRequest`, `UserProfileResponse`; registration in `Program.cs`.
- Tests: `UserTests` (unit), new `UpdateMyProfileUseCaseTests` (unit), new `UserProfileEndpointTests` (integration).
- OpenAPI document gains two routes.
