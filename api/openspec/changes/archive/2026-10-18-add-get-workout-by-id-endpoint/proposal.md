# Proposal

## Why

Clients can only list workouts (`GET /workouts`), which returns every workout the caller may see. A client that holds one workout id, for example from a creation response, has no way to read just that workout. `POST /workouts` also returns no pointer to the created resource.

## What Changes

- Add `GET /workouts/{id}`: returns one workout with its workout exercises, sets and superseries membership, scoped by the caller's role.
- The response does **not** embed catalog exercise data (`name`, `bodyPart`). Each entry carries only the catalog `exerciseId`; the frontend already holds the catalog.
- `POST /workouts` keeps returning `201 Created` and now also sends a `Location` header pointing at `GET /workouts/{id}`.
- No domain, persistence or migration change: `IWorkoutRepository.GetById` already exists.

## Capabilities

### New Capabilities
- `workout-retrieval`: reading a single workout by id, who may read it, and the shape of the response.

### Modified Capabilities
- `workout-creation`: the `201 Created` response now carries a `Location` header with the URL of the new workout.

## Module Classification

- API (`WeightTracker.Api/Endpoints/Workouts`): the new route is **publicly read-only only**. Workouts are a mutable aggregate, not a catalog; only this route reads.
- Application (`WeightTracker.Application/UseCases/Workouts`): the new use case is read-only, but the module is **not catalog-like**. It reads a mutable, owner-scoped aggregate.

## Canonical Template Mapping

- `workout-retrieval` API -> `src/WeightTracker.Api/Endpoints/Workouts/WorkoutsController.cs` (skeleton-backed; inherits `AuthorizedController`, catch routed through `ExceptionMapper`). Behavior of `GetById` mirrors `ExercisesController.GetById`, with `[AllowAnonymous]` dropped because the route is protected.
- `workout-retrieval` Application -> `GetAllWorkoutsUseCase` (same role switch, by id) with `ExerciseUseCase` as the read-only use case reference from `.stpr/template/README.md`.
- `workout-retrieval` tests -> `WorkoutScopingTests` (scoped read, asserts exclusions) and `AuthEndpointsTests` (401 matrix).
- `workout-creation` -> `WorkoutsController.Create` and `WorkoutCreateEndpointTests`.

No conflict with `STPR_INVARIANTS.md` or the template was found.

## State And Mutability

Read-only. No aggregate state changes.

## Roles And Visibility

- ADMIN reads any workout.
- TRAINER reads workouts they own or appear in as trainer.
- USER reads workouts they own.
- A workout that exists but is outside the caller's scope is rejected with `403` (same as the edit use cases); a missing id is `404`.

## Business Identifiers And Mutability

N/A. No new business identifier. The workout `id` is generated by `Id.New()` and is immutable.

## Assumptions

- "Do not include the exercises info" means catalog data only. Workout entries (`id`, `exerciseId`, `effort`, `sets`, `superSeriesId`) stay in the response.
- The new response shape differs from the `GET /workouts` item shape, which keeps `name` and `bodyPart`. The list endpoint is untouched.
- Out-of-scope existing workout is `403`, not `404`, following the "403 when role or ownership forbids" rule in `AGENTS.md`.

## Impact

- `WorkoutsController`: new `GetById` action; `Create` uses a `Location` header; remove the "no route that reads a single workout" remarks.
- New `GetWorkoutByIdUseCase`, new detail response DTO, registration in `Program.cs`.
- New integration and unit tests; `.stpr/template` copies refreshed if they drift.
