# Plan: Refactor Exercises In Workout

## 1. Change Summary

A workout becomes an ordered list of `WorkoutExercise` entries. Each entry references an exercise by
id and carries an `Effort` and an ordered list of `SetPrescription`. Today the `Workout` aggregate holds
whole `Exercise` aggregates as dictionary keys. That breaks the rule "one aggregate never holds a
reference to another aggregate root", so this change removes it.

An exercise can appear only once per workout. Adding it a second time is now rejected, where today its
sets were merged. Each stored row gets an `effort` column, and existing rows are set to `MID`.

`GET /workouts` keeps its route, visibility and scoping. Its only visible change is a new `effort` field
on each exercise in the response. The exercise `name` and `bodyPart` are still returned, now loaded by id
in the use case instead of being carried inside the aggregate.

## 2. Scope

### New domain areas

None.

| Workouts | Application | `GetAllWorkoutsUseCase` also loads the referenced exercises and returns `WorkoutListDTO` |
| Workouts | Infra | `WorkoutExerciseEntity.Effort`, EF config, `WorkoutMapper` (no longer needs exercise rows), `WorkoutRepository` (reconciles by `WorkoutExercise.Id`, no longer loads exercises), seed |
| Workouts | Api | `WorkoutResponse.From` takes the exercise lookup; `WorkoutExerciseResponse` gains `effort`; `ExceptionMapper` entries |
| Exercises | Application, Infra | `IExerciseRepository.GetAllByIds` and its implementation. Read-only addition, with no behavior change to Exercises. |
| Migrations | — | new `AddEffortToWorkoutExercises_202610131437` |
| `.stpr/template` | — | copies of `Workout.cs`, `ExerciseNotInWorkoutException.cs`, `IExerciseRepository.cs` and `WorkoutTests.cs` are synced. `WorkoutExercise.cs` and `Effort.cs` are added as copies. The `README.md` row for `Workouts` and the Arrange/Act/Assert example in `STPR_INVARIANTS.md` §4 are updated. No rule text changes. |

### Explicitly out of scope

- No new endpoints. No API route adds, removes or edits workout exercises; `AddExercise` and
  `RemoveExercise` stay domain-only.
- A `WorkoutExercise` cannot be changed after it is added: there is no effort change, no reordering
  and no editing of sets. To change one, remove it and add it again.
- `SetPrescription` and `SetTarget` are unchanged and gain no validation. An empty set list is still
  accepted, as it is today.
- No exercise-existence check inside the domain. The FK `fk_workout_exercises_exercise` stays the
  backstop. A future use case that adds exercises must validate the id in Application.
- `GET /workouts` scoping, roles and the `401`/`403` behavior are unchanged.
- The `workout_exercise_sets` table, Users, Auth, seeded users and credentials are unchanged.
- Domain events stay dormant.

## 3. Main Concepts

**`Effort`** (new enum, `Domain/Workouts`): `LOW = 1`, `MIDLOW = 2`, `MID = 3`, `MIDHIGH = 4`,
`HIGH = 5`. The values are explicit, as in `BodyParts`, because they are stored as `int`.

**`WorkoutExercise`** (new entity, `Domain/Workouts`), which extends `Entity`:
- `Id: Id`: shared identifier, generated by `Id.New()` in `Create`, immutable.
- `ExerciseId: Id`: reference to the `Exercise` aggregate root by id only. Immutable.
- `Effort: Effort`: must be a defined value. Immutable in this change.
- `Sets: IReadOnlyList<SetPrescription>`: ordered, and exposed as a copy. Immutable in this change.
- `Create(Id exerciseId, Effort effort, IEnumerable<SetPrescription> sets)` sets `IsNew = true`.
  `Rehydrate(Id id, Id exerciseId, Effort effort, IEnumerable<SetPrescription> sets)` sets
  `IsNew = false`. The constructor is private.

**`Workout`** (changed aggregate root):
- `_exercises` changes from `Dictionary<Exercise, List<SetPrescription>>` to `List<WorkoutExercise>`.
- `Exercises` changes to `IReadOnlyList<WorkoutExercise>`, an ordered snapshot copy.
- `AddExercise(Id exerciseId, Effort effort, IEnumerable<SetPrescription> sets)` creates a
  `WorkoutExercise` and appends it to the end.
- `RemoveExercise(Id exerciseId)`
- `Rehydrate(Id, Id userId, Id? trainerId, DateTime, IEnumerable<WorkoutExercise>)`
- `Workout` no longer references `WeightTracker.Domain.Exercises`.

**`WorkoutListDTO`** (new, `Application/UseCases/Workouts`):
`record(IReadOnlyList<Workout> Workouts, IReadOnlyDictionary<Id, Exercise> Exercises)`. It is a read
result with no behavior.

**Exceptions:**

| Exception | Layer | HTTP | Status |
| --- | --- | --- | --- |
| `ExerciseAlreadyInWorkoutException(Id exerciseId, Id workoutId)` | Domain | 409 | new |
| `InvalidEffortException(int value)` | Domain | 400 | new |
| `ExerciseNotInWorkoutException(Id exerciseId, Id workoutId)` | Domain | 404 | retyped from `(string exerciseName, Id)` |

## 4. Module Classification

| Piece | Classification | Consequence |
| --- | --- | --- |
| `Workout` | aggregate root, **mutable** | The only gate to its exercises. Only it has a repository and a mapper. |
| `WorkoutExercise` | entity inside `Workout` | Has identity. Loaded and saved only through `Workout`. No repository and no mapper of its own. |
| `SetPrescription`, `SetTarget` | value objects (unchanged) | Ordered inside `WorkoutExercise.Sets` |
| `Effort` | enum | Checked with `Enum.IsDefined` in `WorkoutExercise.Create` / `Rehydrate` |

| `WorkoutListDTO` | application read record | No validation and no behavior |
| `GetAllWorkoutsUseCase` | use case | One `Execute`. Joining across aggregates for reads belongs in Application. |

No domain service or application service is introduced.

## 6. State And Mutability

| State | Mutability | Changed by |
| --- | --- | --- |
| `Workout.Exercises` (membership and order) | mutable | `AddExercise` (appends), `RemoveExercise` |
| `WorkoutExercise.Id`, `ExerciseId` | immutable; `Id` is system-generated | — |
| `WorkoutExercise.Effort`, `Sets` (including their order) | immutable in this change | only by removing the entry and adding it again |
| `Workout.UserId`, `TrainerId`, `WorkoutDate` | unchanged | — |

Persistence semantics:
- `workout_exercises.id` is now `WorkoutExercise.Id`. Today the mapper invents it on every mapping.
  The id is stable across save and load.
- `Save` on an existing workout reconciles children by `WorkoutExercise.Id`:
  - a surviving entry keeps its row and gets its `position`, `effort` and sets refreshed;
  - an entry that is gone is deleted as an orphan;
  - a new entry is inserted.
  The workout row is never duplicated.
- Sets have no identity, so they are replaced on every save, as they are today.
- Removing and re-adding the same exercise in one unit of work deletes the old row and inserts a new
  one with the same `(workout_id, exercise_id)`. EF Core orders the delete before the insert because the
  unique index is in the model. A repository test guards this. If that test fails, stop and revisit
  the plan. Do not patch it ad hoc.

## 7. Endpoints And Visibility

| Method and route | Visibility | Success | Failures |
| --- | --- | --- | --- |
| `GET /workouts` | authenticated (unchanged) | `200` list of `WorkoutResponse` | `401`, `403` (unchanged) |

- The only contract change is an additive `effort` field (the enum name, such as `"MIDHIGH"`) on each
  `exercises[]` item. `exerciseId`, `name`, `bodyPart`, `sets`, and the order of exercises and sets
  are unchanged.
- Scoping is unchanged:
  - `ADMIN` sees all workouts.
  - `TRAINER` sees the workouts they own and the ones they prescribed, and must not see other users'
    workouts they did not prescribe.
  - `USER` sees only their own workouts, and must not see workouts they don't own, even when they are
    the trainer on them.
- Exercises are joined only for the workouts already in the scoped result, so the join cannot widen
  what a caller sees.

## 8. Business Rules

1. A workout's exercises are ordered. `AddExercise` appends to the end, and the order survives
   persistence.
2. An exercise appears at most once per workout. `AddExercise` with an `exerciseId` that is already
   present throws `ExerciseAlreadyInWorkoutException` and leaves the state unchanged. (This is a change:
   today the sets are merged.) It maps to `409`.
3. Every `WorkoutExercise` has a defined `Effort`. An undefined value throws `InvalidEffortException`,
   which maps to `400`.
4. Sets keep the order they are given: `2x10, 2x8` is not the same as `2x8, 2x10`.
5. `RemoveExercise` with an `exerciseId` that is not in the workout throws `ExerciseNotInWorkoutException`,
   which maps to `404`.
6. `Workout.Rehydrate` rejects duplicate exercise ids with `ExerciseAlreadyInWorkoutException`. The mapper
   wraps that in `PersistenceMappingException`, which returns `500`. The same applies to a stored effort
   that is not defined.
7. Rows that exist before the migration get `effort = MID (3)`.
8. Rules that are unchanged: a trainer cannot own their own workout; an exercise referenced by a workout
   cannot be deleted (`ExistsByExerciseId` still queries `workout_exercises`).

## 9. Technical Decisions

- **Reference by id:** `WorkoutExercise.ExerciseId: Id`. This resolves the existing deviation recorded
  in the exercises-crud plan. A snapshot of the exercise name or body part was considered and rejected,
  because it goes stale when an exercise is renamed.
- **Read join:** `GetAllWorkoutsUseCase` collects the distinct `ExerciseId`s from the scoped workouts and
  calls `IExerciseRepository.GetAllByIds(ids, ct)` once. It returns `WorkoutListDTO`. The repository
  returns `[]` for empty input without querying. A missing exercise cannot happen, because the FK and the
  `ExerciseInUseException` rule prevent it, so no extra exception is introduced.
- **Effort storage:** `workout_exercises.effort`, an `int` that is not null, mapped like `body_part`.
  The migration adds the column with `DEFAULT 3` to backfill existing rows, then drops the default so
  the database never supplies an effort. `Down()` deletes the column.
- **Unique constraint:** `uq_workout_exercises_workout_exercise` is kept. It enforces rule 2 in the
  database.
- **Mapper:** `MapToDomain(WorkoutEntity)` loses its exercises parameter. `MapEffort` mirrors
  `MapBodyPart`. Rehydrating `WorkoutExercise` happens inside the existing `DomainException` →
  `PersistenceMappingException` catch.
- **Wire format:** `effort` is serialized as the enum name, the same as `bodyPart`. No global
  `JsonStringEnumConverter` is added.
- **`Entity` remarks:** the XML remark that cites `Workout` dictionary keys is reworded. Equality
  semantics are unchanged.

## 11. Implementation Constraints

- `Id.New()` is called only inside `WorkoutExercise.Create` and `Workout.Create`, plus the existing
  per-set row ids in the mapper.
- `Workout` and `WorkoutExercise` keep no reference to `Exercise`. No navigation from
  `WorkoutExerciseEntity` to `ExerciseEntity`.
- The repository takes and returns domain types only. `WorkoutRepository` no longer reads `Exercises`.
- The controller injects use cases and `ExceptionMapper` only. `[ProducesResponseType]` is unchanged.
- The EF configuration for `effort` matches the migration column name exactly.
- The `.stpr/template` copies stay byte-identical to `src/` and `test/`.
