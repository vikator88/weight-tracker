## Change

Add `GET /users/me` and `PUT /users/me` endpoints for the authenticated user's own profile

## Objective

Clients (front and backoffice) need to show the logged-in user's data and let them edit their own profile.
Today the only way to learn who the caller is, is decoding the token on the client. These endpoints expose the
caller's profile resolved from the token, and allow editing the fields a user owns.

## Capabilities

- `GET /users/me`: returns the caller's `Id`, `Email`, `Name`, `Surname` and `Role`, resolved from the access token.
- `PUT /users/me`: updates the caller's `Name` and `Surname`, and returns the updated profile with the same shape as `GET /users/me`.
- Both routes are protected and only ever act on the caller. There is no `{id}` in the route.

## Module Classification

- Users (domain) -> mutable aggregate -> `src/WeightTracker.Domain/Users/User.cs`
- Users (application) -> mutable aggregate use cases -> `src/WeightTracker.Application/UseCases/Users` (new folder)
- Users (API) -> REST controller with protected routes -> `src/WeightTracker.Api/Endpoints/Users` (new folder)
- Users (infra) -> existing repository, no schema change -> `src/WeightTracker.Infra/Repositories/UserRepository.cs`

`User` is a mutable aggregate, not a catalog. `GET /users/me` is read-only, but `PUT /users/me` changes persisted state.

## State And Mutability

- `PUT /users/me` changes `users.name` and `users.surname` of the caller.
- `Id`, `Email`, `Role`, `DateBirth`, `PasswordHash` and `CreatedAt` are not changed by this change.
- No new tables or columns, so no migration.

## Business Rules

- `Name` and `Surname` are validated through the existing `PersonName` value object (non-empty after trim, max 100) before the aggregate is mutated.
- Both fields are required on `PUT` (full replacement of the editable profile, not a partial patch).
- The mutation goes through a new aggregate action method, `User.UpdateProfile(PersonName name, PersonName surname)`; the use case never sets properties directly.
- `Role` cannot be changed through this endpoint. The request DTO does not carry it, so a `role` field in the body is ignored, never applied.
- `Email` cannot be changed through this endpoint. The request DTO does not carry it either.
- Invalid `Name`/`Surname` returns `400` through the existing `InvalidPersonNameException` mapping in `ExceptionMapper`.

## Roles And Visibility

- Any authenticated user (`USER`, `TRAINER`, `ADMIN`) can read and edit their own profile.
- No caller can read or edit another user's profile through these routes; the target is always `CurrentUser.Id`.
- A token whose user no longer exists ends with `401`, as `AuthorizedController` already does.

## Business Identifiers And Mutability

- `User.Id` is the technical identifier, generated by `Id.New()`, and immutable.
- `User.Email` is the unique business identifier and stays immutable in this change.

If a future change wants any listed identifier to become mutable, exact persistence semantics must be defined before coding starts.

## Out Of Scope

- Changing the email. It will have its own flow under `/auth` (verification, uniqueness, token impact) in a later change.
- Changing the role. Role management, if needed, belongs to an admin-only flow.
- Changing the password or `DateBirth`.
- Reading or editing another user's profile (`/users/{id}`).
