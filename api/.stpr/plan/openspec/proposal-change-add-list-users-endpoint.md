## Change

Add `GET /users` to list users, scoped by the caller's role

## Objective

Administrators have no way to see who has an account; they can only create users (`POST /users`) and read their
own profile (`GET /users/me`). They need the full list of users of every role. Trainers will eventually need the
list of their athletes, but there is no explicit trainer–athlete relationship yet, so that branch is declared now
and answered as not implemented until the relationship exists.

## Capabilities

- `GET /users` for an `ADMIN`: returns every user, whatever their role, including the caller.
- `GET /users` for a `TRAINER`: reserved for "my athletes"; answers that the feature is not implemented yet.
- `GET /users` for a `USER`: forbidden.

## Module Classification

- Users (domain) -> mutable aggregate -> `src/WeightTracker.Domain/Users/User.cs` (no change expected)
- Users (application) -> mutable aggregate use case (read) -> `src/WeightTracker.Application/UseCases/Users`
- Users (API) -> REST controller with protected routes -> `src/WeightTracker.Api/Endpoints/Users/UsersController.cs`
- Users (infra) -> existing repository, new read method, no schema change -> `src/WeightTracker.Infra/Repositories/UserRepository.cs`

`User` is a mutable aggregate, not a catalog. This change only adds a read path; it is publicly read-only here but
the aggregate keeps changing through signup, `POST /users` and `PUT /users/me`.

## Canonical Template Mapping

- `GetAllUsersUseCase` -> `src/WeightTracker.Application/UseCases/Workouts/GetAllWorkoutsUseCase.cs` -> nearest
  role-scoped list: receives the caller's id and role and branches on the role (`ADMIN` all, other roles scoped)
- `IUserRepository.GetAll` / `UserRepository.GetAll` -> `IWorkoutRepository.GetAll` / `WorkoutRepository.GetAll` ->
  same repository read shape, mapping to domain inside the repository
- `UsersController.GetAll` -> `.stpr/template/src/WeightTracker.Api/Endpoints/Workouts/WorkoutsController.cs`
  (`GetAll`) -> protected `AuthorizedController` list action, every catch through `ExceptionMapper.Map`
- Role gate -> `src/WeightTracker.Api/Endpoints/RequireRoleAttribute.cs` -> `[RequireRole(Role.ADMIN, Role.TRAINER)]`
  answers `401` before `403`, as `POST /users` already does
- Response DTO -> `src/WeightTracker.Api/Endpoints/Users/Dtos` -> list of the existing user DTO shape built with `From(User)`
- Tests -> `test/WeightTracker.Unit/Application/Workouts/GetAllWorkoutsUseCaseTests.cs` and
  `test/WeightTracker.Integration/Users/CreateUserEndpointTests.cs` -> role-branch unit tests with mocked ports,
  and the `401`/`403` matrix with response-content checks

## State And Mutability

- Nothing changes state. `GET /users` only reads `users`.
- No new tables or columns, so no migration.

## Business Rules

- `ADMIN`: receives every stored user, of every role (`USER`, `TRAINER`, `ADMIN`), including themselves.
- `TRAINER`: the use case throws a dedicated "not implemented" application exception, because no trainer–athlete
  relationship exists to scope the list. No user data is returned.
- `USER`: rejected with `403` by `[RequireRole]` before the use case runs.
- The use case also rejects a `USER` role with `UnauthorizedOperationException` (`403`), so the rule does not
  depend only on the HTTP attribute.
- The list has a stable order: by `Email` ascending.
- No filtering, search or pagination parameters.

## Roles And Visibility

- `ADMIN`: `200` with all users.
- `TRAINER`: `501 Not Implemented` (see Notes for the exception choice).
- `USER`: `403`.
- Unauthenticated or invalid token: `401`.
- Each item exposes `Id`, `Email`, `Name`, `Surname` and `Role`. Never the password hash, refresh tokens or
  `CreatedAt`.

## Business Identifiers And Mutability

- `User.Id` is the technical identifier, generated by `Id.New()` inside `User.Create`, and immutable. Not
  affected by this change.
- `User.Email` is the unique business identifier and is immutable after creation. Not affected by this change.

If a future change wants any listed identifier to become mutable, exact persistence semantics must be defined before coding starts.

## Out Of Scope

- The trainer–athlete relationship and the real "my athletes" list. A later change defines the relationship and
  replaces the not-implemented branch.
- `GET /users/{id}`, editing, deleting or disabling users, and changing roles.
- Pagination, filtering by role, and search.
- Any front change (backoffice screen, `core` use case). That is a separate plan in `front/` after the OpenAPI
  snapshot refresh.
- `GET /users/me`, `PUT /users/me` and `POST /users` must not change.

## Notes

- Exception for the trainer branch: add a dedicated application exception (for example
  `TrainerAthletesNotImplementedException`, or a generic `FeatureNotImplementedException`) in
  `Application/Exceptions`, mapped explicitly in `ExceptionMapper` to `501 Not Implemented`. Do not throw the
  framework `NotImplementedException`: `ExceptionMapper` would answer it as `500`, which reads as a server fault
  instead of a known, deliberate gap. Confirm the name and the `501` status at proposal time.
- Response DTO: reuse `UserProfileResponse` for each item. It already has exactly `Id`, `Email`, `Name`, `Surname`
  and `Role` with a `From(User)` factory, so no new DTO is needed. `DateBirth` stays out of the list, as it is out
  of the profile reads.
- The use case receives the caller's `Id` and `Role` from `CurrentUser`, as `GetAllWorkoutsUseCase` does; the `Id`
  will be needed when the trainer branch is implemented.
- Add `GetAll(CancellationToken)` to `IUserRepository` and `UserRepository`, ordered by email, returning domain
  `User` objects.
- Register `GetAllUsersUseCase` in `Program.cs`.
- Declare `[ProducesResponseType]` for `200` (list of `UserProfileResponse`), `401`, `403` and `501`.
- Tests to add:
  - Unit `GetAllUsersUseCase`: `ADMIN` returns everything the repository returns; `TRAINER` throws the
    not-implemented exception and never calls the repository; `USER` throws `UnauthorizedOperationException` and
    never calls the repository.
  - Integration `GET /users`: `401` without token and with an invalid token; `403` for the seeded `USER`; `501`
    for the seeded `TRAINER` with no user data in the body; `200` for the seeded `ADMIN` with all seeded users of
    the three roles, ordered by email, including a user created with `POST /users` in Arrange; each item has
    exactly `id`, `email`, `name`, `surname`, `role`.
  - `ExceptionMapper` test for the new exception -> `501`.
  - OpenAPI document test: `GET /users` is secured and declares `200`, `401`, `403`, `501`.
- OpenAPI snapshot changes (new operation on `/users`); the front refreshes it in its own plan.
- No deviations from the mapped template references are allowed.
