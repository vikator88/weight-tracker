## Change

Add `POST /users` so an administrator can create users of any role (`USER`, `TRAINER`, `ADMIN`)

## Objective

Today the only way to create a user is self-service `POST /auth/signup`, which forbids `ADMIN` and logs the new
user in. Administrators need to create accounts on behalf of others, including other administrators, without
the endpoint issuing any session for the created user.

## Capabilities

- `POST /users`: creates a user with `Email` and `Password` (required) and `Name`, `Surname` and `DateBirth`
  (optional), with the `Role` chosen by the caller.
- Returns `201` with the created user's data. No access token, refresh token or any other authentication object.
- Only callable by an authenticated `ADMIN`.

- Users (domain) -> mutable aggregate -> `src/WeightTracker.Domain/Users/User.cs` (no change expected; `User.Create` already covers it)
- Users (application) -> mutable aggregate use case -> `src/WeightTracker.Application/UseCases/Users`
- Users (API) -> REST controller with protected routes -> `src/WeightTracker.Api/Endpoints/Users/UsersController.cs`
- Users (infra) -> existing repository, no schema change -> `src/WeightTracker.Infra/Repositories/UserRepository.cs`

`User` is a mutable aggregate, not a catalog. This change only adds a creation path.

## State And Mutability

- `POST /users` inserts a row in `users`.
- No refresh token is created, so `refresh_tokens` is not touched.
- No new tables or columns, so no migration.

## Business Rules

- Only an `ADMIN` caller can create users; `USER` and `TRAINER` get `403`.
- The caller can set any `Role`: `USER`, `TRAINER` or `ADMIN`. `AdminSignupNotAllowedException` does not apply here.
- `Role` is required. An unknown role value is rejected with `400` by model binding.
- `Email` is required and validated by the `Email` value object. A malformed email returns `400`
  (`InvalidEmailException`), not the `401` that signup uses to avoid enumeration: the caller is an authenticated admin.
- `Email` must be unique: an existing email returns `409` through `EmailAlreadyExistException`.
- `Password` is required and validated by the `Password` value object; a weak password returns `400` through
  `PasswordNotStrongEnoughException`. It is hashed with `IPasswordHasher` before reaching the aggregate.
- `Name` and `Surname` are optional. When present, they are validated by `PersonName` (non-empty after trim,
  max 100), and invalid values return `400` (`InvalidPersonNameException`). When absent, `PersonName.Empty()` is
  stored, as signup does.
- `DateBirth` is optional. When absent, `DateOnly.MinValue` is stored, as signup does. No date range rule is added.
- The created user is not logged in; the caller's session is unaffected.

## Roles And Visibility

- `ADMIN`: can create users of any role.
- `TRAINER`, `USER`: `403`.
- Unauthenticated or invalid token: `401`.
- The response exposes `Id`, `Email`, `Name`, `Surname`, `DateBirth` and `Role` of the created user. Never the
  password or its hash.

## Business Identifiers And Mutability

- `User.Id` is the technical identifier, generated by `Id.New()` inside `User.Create`, and immutable.
- `User.Email` is the unique business identifier and is immutable after creation.

If a future change wants any listed identifier to become mutable, exact persistence semantics must be defined before coding starts.

## Out Of Scope

- Listing, editing, deleting or disabling users (`GET/PUT/DELETE /users/{id}`).
- Changing an existing user's role or password.
- Invitations, email verification or forcing a password change on first login.
- Any front change (backoffice screen, `core` use case). That is a separate plan in `front/` after the snapshot refresh.
- `POST /auth/signup` must not change: it keeps forbidding `ADMIN` and keeps logging the user in.
